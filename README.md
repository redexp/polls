# Соціологічна служба Черкаського інституту міста

Цим проєктом Громадська організація «Черкаський інститут міста» започатковує новий підхід до проведення соціологічних досліджень, які з часом мають замінити старі методи вивчення громадської думки.

Завдяки цифровим інструментам соціологічні дослідження можуть стати:

- Більш масовими, а отже — якіснішими, з меншими статистичними похибками, краще відображати суспільну думку, бо тепер опитуваннями легше досягти радикально більшої аудиторії
- Дешевшими та швидшими, бо вже не потрібно утримувати великі команди інтерв’юерів, зустрічатися з опитуваними особисто і вручну аналізувати анкети
- Достовірнішими, бо застосування цифрового підпису та інших цифрових ідентифікаторів унеможливлює наданя неправдивих даних людьми, які погодилися взяти участь в опитуванні, та відсіює людей, які не є цільовою групою опитування за місцем проживання, дозволяє уникнути фальшування, дублювання опитувальників

## Основі можливості

- Декілька варіантів відповіді з можливістю обрати один чи декілька варіантів.
- Ідентифікація через [BankID](https://bank.gov.ua/ua/bank-id-nbu) унеможливлює створення фальшивих відповідей.
- Опціональне обмеження для участі у опитуваннях по місцю проживання (наприклад тільки у місті Черкаси).
- Окремі опитування можуть містити (за попереднім попередженням і згодою опитуваних) список імен тих, хто взяв участь в опитуванні, для того, щоб результати таких опитувань могли виконувати роль легальної, достовірної публічної демонстрації громадянської позиції на зразок петицій, які надалі можуть бути передані до органів місцевого самоврядування для відповідного реагування.

## Обмеження

- По місцю реєстрації у місцевості вказаній у конфігурації.
- Відповіді змінювати можливо лише на протязі 10 хвилин.

## Технічні характеристики

- Опитування можна створювати двома способами:
  - **вручну**, редагуванням `md` файлів на сервері — тоді жоден вебінтерфейс до опитувань доступу не має;
  - **через адмінку** `/admin`, доступ до якої мають лише BankID-акаунти зі списку `AUTH_ADMINS`.

  Файли лишаються джерелом правди в обох випадках, тож адмінка не створює окремого стану, який можна було б розсинхронізувати. Але вона все ж є додатковою поверхнею атаки: історія змін опитувань не ведеться, тому список `AUTH_ADMINS` варто тримати мінімальним. Якщо адмінка вам не потрібна — просто не заповнюйте `AUTH_ADMINS`, і всі її запити відхилятимуться.
- Питання пишуться у форматі [md](https://uk.wikipedia.org/wiki/Markdown), автоматично створюються статичні html файли за допомогою фреймворка [Astro](https://astro.build)
- Динамічна частина сайту написана на TypeScript і _без_ використання бібліотек типу React. Причини:
  - На сайті нема складної логіки - буквально форми і запити
  - В такому коді розбереться буквально буть-хто, з будь-яким бекграундом
- Відповіді зберігаються на сервері у базі даних [SQLite](https://sqlite.org) разом з ім'ям, та ідентифікатором [BankID](https://bank.gov.ua/ua/bank-id-nbu) громадянина. 
- Окремо від імені (тобто анонімно), зберігається вік, стать та район міста (у форматі [Plus Code](https://uk.wikipedia.org/wiki/Відкритий_код_розташування) тобто не точна адреса, а приблизне місце розташування) того хто залишив відповідь для статистичних висновків.
- Оформлення — теми [Bootswatch](https://bootswatch.com) для Bootstrap: [Flatly](https://bootswatch.com/flatly/) світла і [Darkly](https://bootswatch.com/darkly/) темна. Перемикаються **автоматично** за системним налаштуванням користувача (`prefers-color-scheme`): кожна тема підключена окремим `<link>` зі своєю `media`, тому діє рівно одна. Обидві з пакета `bootswatch`, а не з CDN, щоб сторонній домен не потрапляв у критичний шлях завантаження.
  - Половина змінних Bootstrap 5.3 (рамки, поля, посилання — 49 штук) живе під селектором `[data-bs-theme=dark]`, а атрибут медіа-запитом не виставити, тому в `Base.astro` є короткий інлайновий скрипт, який ставить його за тим самим медіа-запитом. Без JS темна тема все одно застосується, лише рамки будуть світлого відтінку.
  - **Увага:** самі теми містять `@import` шрифту Lato з `fonts.googleapis.com`, тобто зовнішній запит на кожне завантаження сторінки все одно є. Якщо це небажано — приберіть цей рядок з теми (шрифт відкотиться на системний) або покладіть Lato у `public/` і підключіть локально.
  - Darkly навмисно робить поля введення світлими (`.form-control{background-color:#fff}` — це дизайн теми, не помилка). Якщо в темній темі хочеться темних полів, це треба перекривати окремо.
- Запити від браузера обробляються сервером [Express](https://expressjs.com)
- Сервер не використовує cookie. Замість цього використовується технологія [JWT](https://jwt.io)

## Запуск проєкту у режимі розробки

1. Скопіюйте проєкт `git clone git@github.com:redexp/polls.git && cd polls`
2. Встановіть пакети `npm install` або `pnpm install` (саме lock файл [pnpm](https://pnpm.io/installation) знаходиться у проєкті)
3. Створіть актуальну базу даних `npm run migrate`. Буде створено файл `database.sqlite`.
4. Створіть ключі для шифрування статистичних даних `npm run keys`. Ключ `statistic_private_key.pem` треба перемістити у безпечне місце окремо від цього проєкту.
5. Запустіть astro фреймворк `npm start`
6. Запустіть сервер API `npm run server`
7. Запустіть сервер який вдає BankID `npm run bankid`
8. Відкрийте сторінку http://localhost:4321

Адмінка — на http://localhost:4321/admin. Щоб отримати до неї доступ, додайте свій ІПН у `AUTH_ADMINS` (JSON-масив, наприклад `AUTH_ADMINS=["1234567890"]` у `.env`).

Тести (парсер опитувань, генератор, валідація) — `npm test`. Вони на вбудованому в Node тест-раннері, без додаткових залежностей.

## Налаштування

Налаштування серверу API знаходяться у папці `server/config` (основні — в `server/config/index.js`, окремо `bankid.js`, `auth.js`, `age-groups.js`). Усі налаштування можуть бути переписані змінними середовища. Наприклад наступні налаштування
```js
const config = {
	bankid: {
		dev_port: 8001,
		url: '',
		client_id: '',
		client_secret: '',
		dataset: 51,
	},
    //...
};
```
Можут бути переписані змінними середовища `BANKID_DEV_PORT`, `BANKID_URL`, `BANKID_CLIENT_ID` і т.д. Також ви можете створити файл `.env`.

### Maps

Для того, щоб сгенерувати [Plus Code](https://uk.wikipedia.org/wiki/Відкритий_код_розташування) з адреси - необхідний сервіс, який дасть координати (у вигляді latitude та longitude) з цієї адреси, а вже потім вони перетворюються на код у вигляді `8GXJC3V5+`. На даний момент сервіс [Mapbox](https://mapbox.com) дає можливість робити до 100 000 запитів на місяць безкоштовно, в той час як Google Maps API дає лише 10 000. Тому наразі використовується цей сервіс. Все що потрібно - це створити `access_token`.

## Запуск проєкту у робочому режимі

1. Сгенеруйте статичні файли `npm run build`. Будуть створені файли у папці `dist`. Як правило їх копіюють в папку `public` на веб сервері і налаштовують `nginx` для того щоб він їх віддавав.
2. Скопіюйте папку `server` на ваш веб сервер і запустіть `node server/index.js`

### Публікація з адмінки

Якщо ви користуєтесь адмінкою, збірку запускає вона сама, і `dist` перетворюється на **симлінк**:

- кожна збірка складається в окрему теку `builds/<штамп часу>/`;
- після успішної збірки симлінк `dist` переставляється на неї, тому конфіг `nginx` змінювати не потрібно — він і далі дивиться на `dist`;
- зберігаються 3 останні збірки, і в адмінці є кнопка «Відкатити», яка просто переставляє симлінк назад;
- якщо збірка впала, симлінк не переставляється, а тека невдалої збірки видаляється — сайт лишається на попередній версії.

Теки задаються змінними `BUILDS_DIR` (типово `builds` у корені проєкту) і `DIST_LINK` (типово `dist`). При першому запуску наявна тека `dist` не видаляється, а переноситься у `builds` — тому на неї теж можна відкотитись.

Файлова система мусить дозволяти симлінки. На Linux це так за замовчуванням; на Windows потрібні окремі права, але в режимі розробки збірка й не запускається — `astro dev` підхоплює зміни сам.

### Картинки опитувань

Картинки, додані через адмінку, лежать **поза** збіркою — у `UPLOADS_DIR` (типово `uploads` у корені проєкту), інакше кожна копіювалась би в усі три збірки і зникала б разом із ними. Тому nginx має віддавати цю теку окремим `location`:

```nginx
location /img/polls/ {
    alias /шлях/до/polls/uploads/;
    expires max;
    add_header Cache-Control "public, immutable";
}
```

Файли незмінні — кожне завантаження дає нове ім'я, — тому кешувати їх можна назавжди. Тимчасову теку `UPLOADS_TMP_DIR` (типово `uploads-tmp`) роздавати не треба.

## Редагування опитувань

Усі опитування — це `md` файли у папці `src/polls`. В цій же папці ви знайдете приклади. Редагувати їх можна вручну або через адмінку `/admin` — формат один і той самий.

**Імʼя файла — це ідентифікатор опитування у базі даних**, тож не змінюйте його у процесі збору відповідей. Ідентифікатор унікальний **глобально**, включно з підтеками: `old.md` і `past/old.md` одночасно існувати не можуть. Адмінка блокує зміну ідентифікатора після першого голосу, бо `statistic` привʼязана до односторонього хешу, який його включає.

### Налаштування опитування

На початку файлу:

```yaml
---
expire: 2027-12-31   # дата закінчення опитування
public: true         # чи зберігати імʼя разом з відповіддю (типово опитування анонімні)
draft: false         # чернетка: не потрапляє ні в збірку, ні на сервер
---
```

### Варіанти відповіді

Кожен варіант — окремий рядок. У квадратних дужках — значення, яке зберігається у базі, далі підпис, який бачить людина:

```md
## Заголовок опитування

Текст опитування

[перша] Відповідь 1
[друга] Відповідь 2
[інше]+ Свій варіант

-------------------

(так) Так
(ні) Ні
```

- `[значення] Підпис` — можна вибрати кілька варіантів (checkbox);
- `(значення) Підпис` — можна вибрати лише один (radio);
- `+` одразу після дужки — під варіантом зʼявиться поле, у яке людина впише свій текст;
- рядок з `---`, **відділений порожніми рядками**, починає нову групу варіантів. Порожні рядки обовʼязкові: `---` одразу під рядком тексту markdown розбирає як заголовок, а не як розділювач.

Значення мають бути унікальними в межах усього опитування, і в одній групі не можна змішувати `[...]` та `(...)`.

### Обмеження кількості відповідей

Окремий рядок у межах групи:

```md
{1-3}
[a] Варіант A
[b] Варіант B
[c] Варіант C
```

- `{мінімум-максимум}`, завжди два числа;
- `{0-3}` означає, що групу можна пропустити (це і є «необовʼязкова група»);
- без директиви: для `[...]` — від однієї відповіді без верхньої межі, для `(...)` — рівно одна;
- для `(...)` максимум більший за 1 — це помилка, бо вибрати можна лише один варіант.

Обмеження перевіряється і в браузері, і на сервері.

### Картинки

У тексті картинка — це посилальне зображення markdown, а її адреса винесена в кінець файлу:

```md
Текст опитування

![Картинка 1][k3j9x2ab]

[a] Варіант A
[b] Варіант B

[k3j9x2ab]: /img/polls/0123456789abcdef.webp
```

Адмінка робить це сама: файл можна перетягнути в будь-яке текстове поле (або натиснути «Картинка» біля вступного тексту), під полем зʼявляється мініатюра з хрестиком, а в текст стає лише короткий токен `![Картинка N][…]`. На сервер файл потрапляє **разом зі збереженням** опитування: він ужимається до 1600px по ширині, конвертується у webp і втрачає метадані (зокрема GPS з EXIF). Приймаються png, jpg і webp до 10 МБ. Картинка, токен якої прибрали з тексту, при наступному збереженні видаляється з диска.

Файли лежать у теці `UPLOADS_DIR` (типово `uploads` у корені проєкту) поза збіркою, тимчасові — в `UPLOADS_TMP_DIR` (типово `uploads-tmp`). Адреси у файлах опитувань починаються з `/img/polls/`; у режимі розробки їх віддає сервер API, а в робочому — nginx (див. «Запуск проєкту у робочому режимі»).

Картинка, поставлена **одразу під рядком варіанта**, стає частиною його підпису — тобто клікабельною. Щоб вона була окремим блоком, лишіть перед нею порожній рядок.

Написані руками картинки з іншими адресами (`![…](https://…)` чи власне визначення `[x]: https://…`) адмінка не чіпає.

### Візуальний редактор

Перемикач «Візуальний редактор» праворуч від вступного тексту замінює всі текстові поля форми редактором на [Tiptap](https://tiptap.dev) з панеллю: жирний, курсив, списки, картинка. Файл опитування від цього не змінюється — редактор читає і пише той самий markdown, а стан перемикача зберігається лише в браузері.

### Що не можна змінити після появи голосів

Додавати нові варіанти можна — старі відповіді лишаються валідними. А от **видаляти, перейменовувати** значення або **змінювати тип групи** — ні: наявні відповіді після цього неможливо інтерпретувати. Адмінка це блокує і показує, скільки голосів було б знищено.

Видалення опитування з адмінки знищує його відповіді і статистику **назавжди**, тому вимагає ввести ідентифікатор опитування вручну.

### Перехід зі старого синтаксису

Раніше обмеження кількості відповідей задавалось словами в тексті («Оберіть 3», «від 1 до 3 варіантів»), поле для власного тексту — суфіксом `-інше` у значенні, а необовʼязкові групи — полем `optional` у налаштуваннях. Усе це замінено на `{мінімум-максимум}` і `+`.

Щоб перевести наявні опитування:

```bash
npm run migrate-polls
```

Скрипт дописує `+` там, де значення закінчується на `-інше`, переносить обмеження з тексту у `{мінімум-максимум}` (сам текст лишає — формулювання часто несе більше сенсу, ніж два числа), перетворює `optional` на `{0-N}` і зберігає копію кожного зміненого файлу поруч, з розширенням `.bak`. Спочатку можна подивитись, що саме зміниться:

```bash
node bin/migrate-polls.js --dry
```

Значення в базі даних не змінюються: `+` дописується **після** дужки, тому `answers.value` і `statistic.value` лишаються тими самими.
